# 渐进迁移

## 基线和切口

记录版本或内容标识、可复现构建、受影响行为与数据格式。保留用户已有改动，不把历史文档当成最新实现。不能构建时区分基线故障与本次修改。

优先定位重复规则、平台引用、解析原始响应的 UI、分散状态写入点；不自动把最大文件当成首要问题。按依赖安排切口，不机械套固定层序。

典型路线：提取可测试规则与模型 → 建立必要契约 → 接入适配 → 集中用例提交 → 迁移消费者 → 删除旧逻辑。实际可从收益高、风险低的替换点开始。

每个切口核对前后等价行为；有意改变时记录理由与验收标准。过渡期可留临时适配，不能留两个争夺权威状态的写入路径。

## 数据与更新兼容

改持久化格式时定义 schema 版本、触发条件、失败处理、恢复与旧样本。区分旧值、缺失值和零值，必要时保留备份。回退代码是否能读新格式另行验证，不能默认可逆。

移动应用覆盖安装需核对应用标识、签名证书与版本约束；包名相同不代替签名一致。缺原签名时完成其他工作，明确可安装与可覆盖安装构建的差别，不制造新密钥宣称兼容。

桌面或服务项目核对配置路径、凭据、数据库和接口兼容，不套 APK 要求。真实凭据不进入技能、测试材料、文档或日志。

## 控制规模

避免同时重写主题、更换技术栈、升级依赖或新增功能，除非必要或已授权。删除无消费者的旧实现，检查绕过边界的旁路；兼容代码标明移除条件。

“保留行为”需样本比较，“更易扩展”需真实依赖和变化检查，不能靠接口数量证明。阻塞时交付已完成部分及缺口，不把部分迁移描述为全部完成。
