# 软件架构设计与渐进迁移

## 工作原则

沿用 reasoning-workflow 的任务理解、证据与执行控制；本技能只补充架构判断。若该技能不可用，仍完成专项工作，不伪称已经调用。遵循用户当前范围与工程约定，不把架构偏好变成额外审批。

先确定要保护的行为、数据与未来变化，再选择边界。区分设计目标、源码事实、已运行验证及未知项。用户反馈“没发现问题”可支持被测使用路径正常，不能证明依赖方向、竞态与迁移全部通过。

不要把单个项目的包名、版本号、系统、业务字段、签名密钥或尚未验证的实现固化为通用规则。实际工程和当前记录优先于历史记忆。

## 1. 读取基线并校准规模

旧项目先读取实际最新源码、AGENTS.md、构建与依赖配置、架构记录、最近修改和验证记录。定位业务入口、数据接入、存储、状态提交、平台发布与渲染路径；找不到源码时只做有界设计，不宣布完成迁移。

新项目确定主要用例、状态所有权、持久化需求、平台与数据源、部署方式、维护期限及关键约束。不要为了未来“可能”扩展无限加层。

| 情况 | 默认选择 |
|---|---|
| 一次性脚本、少量转换，无长期维护需求 | 简单函数与必要的 I/O 分离；不建立空壳层 |
| 单平台、少量业务的长期应用 | 清晰模块或按功能组织；分离业务规则和外部副作用 |
| 复杂业务、多平台、多接入或高回归成本 | 明确核心契约、用例协调、外部适配与展示边界 |

新增接口、模块、映射或服务前，说明它隔离的实际变化或支持的验证。纯委托空壳、重复模型和无消费者的抽象应删除或合并。分层与按功能组织可以组合；不要用目录名称证明解耦。

## 2. 定义契约与依赖方向

复杂项目阅读 [边界与状态契约](references/boundaries-and-state.md)，按需要选择职责，而非固定物理五层：

| 职责 | 负责 | 避免 |
|---|---|---|
| Core / Domain | 领域模型、不变量、业务规则 | UI、平台 SDK、数据库与传输对象 |
| Application / Repository 协调 | 用例、查询与提交协调、事务或并发语义 | 布局与具体平台能力实现 |
| Data / Provider | 外部响应解析、存储或协议适配 | 展示决策和跨表面重复业务规则 |
| Platform / Infrastructure | 凭据、网络、缓存、时钟、调度、权限与系统接入 | 自行改写领域语义 |
| Presentation | 展示状态、布局、交互和平台渲染 | 自行解析接口、绕过用例修改权威状态 |

依赖朝稳定策略与契约；让外部实现依赖被其服务的契约。组装入口连接具体实现。区分数据流、源码依赖和运行调用，避免双向引用或循环。

不要强求 Repository 命名或把所有业务塞入 Repository：可用 UseCase、Application Service 或现有合适名称。持久化集合可用 Repository，复杂流程可另设用例。允许多个独立领域各有状态所有者。

关键契约写清输入、输出、所有权、身份、时间语义、错误、取消和副作用；保持领域错误与用户提示分离。跨语言优先复用契约、规格与测试向量，不承诺源码直接复用。

## 3. 建立可追溯的变更方案

列出真实违规点及证据位置，按用户影响、数据风险、修改牵连与迁移成本排序。本次选择少量高价值切口，写明前后职责、保持的行为、兼容边界、验证方法和回退方式。

新项目先实现一条端到端用例和其失败路径，再扩展结构。旧项目阅读 [渐进迁移](references/incremental-migration.md)，逐步移交权威状态与业务逻辑。用户要求实施时完成范围内修改，不停留在建议；只要求设计时不擅自改工程。

不全面重写 UI，不增加无关功能，不因架构任务默认改变版本、包名、签名、数据库身份或发布方式。遵循项目规则与用户授权；要求可安装产物时验证构建与升级兼容。

## 4. 用行为与结构双重验证

阅读 [验收与交付](references/verification-and-delivery.md)，按改动选择必要检查：

- 结构：检查实际依赖、外部调用和状态写入点；能否独立构建或测试核心；检查传递依赖，不能只搜 import。
- 行为：正常、失败、恢复及受影响边界；涉及共享异步状态时覆盖乱序、取消、账户切换与过期提交。
- 兼容：有持久化迁移或安装更新时验证旧数据、标识、配置与恢复路径。
- 展示：多表面消费同一业务状态时核对同版本结果；允许布局、显示精度及平台刷新延迟不同。

优先用现有测试、构建工具和适合技术栈的依赖检查。只有文本搜索、静态审阅、模拟数据或手工正常路径时，明确覆盖边界。不能用测试次数、编译成功、模型自评或文件改名替代结果证据。

## 5. 收口并保留可继续的记录

更新现有架构记录：已迁移、暂留耦合、例外及原因、后续触发条件。没有记录且确有维护需求时建立精简说明，避免重复文档。

交付适合任务的源码与可运行产物，说明具体改动、验证命令与结果、未验证项及剩余风险。区分“方案已定”“代码已改”“结构已验证”“行为已验证”“目标环境待验证”。只在证据覆盖本次约定范围时称该范围验收通过。

技能指导执行；工程模板提供起步代码；实际构建规则与测试约束结果。不要声称本技能自身强制了所有工程的依赖边界。
